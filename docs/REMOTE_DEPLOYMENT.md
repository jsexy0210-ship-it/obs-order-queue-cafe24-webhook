# 어디서든 시작하는 운영 배포

GitHub Actions의 **Deploy production remotely → Run workflow**로 모바일/집/사무실에서 동일한 운영 서버에 배포합니다. 실행기는 GitHub의 Ubuntu 환경이며 대상은 기존 Windows 운영 PC입니다. 운영 PC는 켜져 있고 SSH로 접근 가능해야 합니다. 이 구성은 꺼진 PC를 켜거나 인터넷 연결을 복구하지 않습니다.

## 현재 적용 범위

- Windows + Node.js 22.18.0 + PM2 `mangotcg-admin`인 기존 운영 구성에 대응합니다.
- SSH 연결과 실제 원격 배포는 별도 검증이 필요합니다. 워크플로 파일 추가만으로 접속 구성이 완료되지는 않습니다.
- 집/사무실 PC를 서로 다른 운영 DB로 번갈아 배포하지 않습니다. 실제 도메인이 연결된 **하나의 운영 대상**을 지정합니다.
- 카페24 토큰, 주문/지급/회수 원장을 별도 DB로 복사하거나 초기화하지 않습니다. 새 릴리스의 `data`는 원본 폴더에 대한 junction입니다. 기존 `.env.local`만 값 변경 없이 새 릴리스로 복사합니다.
- 빌드 단계는 원본 DB에 접근하지 않습니다. 지급 스위치도 변경하지 않습니다.

## 최초 연결

대상 Windows 서버에서 기존 PM2 프로세스를 소유한 계정으로 OpenSSH 접속이 가능해야 합니다. SSH 호스트키를 관리자가 기존의 신뢰 가능한 접속 수단으로 확인하고, 배포 전용 키를 사용합니다. 자동 호스트키 승인이나 검증 해제는 하지 않습니다.

GitHub 저장소의 `production` Environment에 다음 Secrets를 등록합니다. 비밀번호/개인키는 채팅·코드·로그에 넣지 않습니다.

| Secret | 값 |
|---|---|
| `MANGO_DEPLOY_HOST` | 실제 운영 PC로 연결되는 SSH 호스트 |
| `MANGO_DEPLOY_PORT` | SSH 포트, 생략 시 22 |
| `MANGO_DEPLOY_USER` | 기존 PM2 프로세스의 소유 계정 |
| `MANGO_DEPLOY_SSH_KEY` | 해당 계정용 배포 개인키 |
| `MANGO_DEPLOY_KNOWN_HOSTS` | 신뢰 가능한 경로에서 확인한 OpenSSH known_hosts 행. 비표준 포트는 `[host]:port` 형식 |
| `MANGO_DEPLOY_APP_PATH` | 원본 `data/cardbreak.db`가 있는 기존 Windows 앱 절대 경로 |

환경 보호 규칙이나 승인 요구가 있다면 그대로 적용됩니다. 기존 토큰 암호화 키와 환경파일은 서버에 유지합니다. 포트 개방·공유기·VPN 설정은 대상 네트워크에 맞춰 별도로 확인해야 합니다.

## 전환 순서

1. 현재 운영 대상, 원본 DB 위치, SSH 호스트키를 확인하고 Secrets를 등록합니다.
2. 기존 사무실 배포가 `queued`이면 해당 대기 실행을 취소합니다. 실행 중인 배포는 끝날 때까지 기다립니다. 두 배포 방식은 `mangotcg-production` 동시 실행 제한을 공유합니다.
3. `Deploy production remotely`를 수동 실행합니다. 항상 최신 main을 배포합니다.
4. Actions 성공, 운영 도메인, 로그인, 주문·적립금 원장과 서버 지급 조건을 확인합니다.
5. 첫 원격 배포 검증 후 **저장소 Actions Variable** `MANGO_REMOTE_DEPLOY_ENABLED=true`를 설정합니다. 이후 main push는 원격 방식만 실행하고 기존 사무실 러너 방식은 건너뜁니다. 전환 전에는 기존 자동배포를 유지합니다.

## 실패 처리

연결·설정·Node 버전·DB 위치·빌드 검사가 실패하면 기존 앱 전환 전 중단합니다. 전환 후 로컬 로그인 HTTP 200 및 PM2의 실행 경로를 확인하며, 실패하면 이전 PM2 설정으로 복귀합니다. DB를 이전 사본으로 복원하지 않습니다. 배포는 적립금 실제 지급·중복 웹훅·취소/환불 검증을 대신하지 않습니다.

릴리스 폴더는 롤백을 위해 보존합니다. 정리는 실행 중인 릴리스와 직전 정상 릴리스를 확인한 운영자가 수행합니다. 실제 운영 연결 검증 전에는 이 구성이 운영에서 검증됐다고 간주하지 않습니다.
